# 포트폴리오 사이트 — AI 에이전트 작업 규칙

이 문서는 이 저장소에서 작업하는 AI 에이전트의 행동 규칙이다.
AI는 Issue, 브랜치, 구현, 검증, PR까지 수행한다.
**검토와 승인은 사용자(작업자)가 한다. AI는 승인 단계에서 반드시 멈춘다.**

## 2. 프로젝트 사실 (변경되면 이 절을 갱신)

- **목적:** 프론트엔드 개발자 개인 포트폴리오. 정적 사이트. 백엔드·DB 없음.
- **스택:** Next.js 16 (App Router), React 19, TypeScript, CSS Modules + CSS Variables, `motion`, `next-intl`, `next-themes`, `lucide-react`, Prettier, ESLint. Playwright는 UI 완성 후 도입.
- **사용하지 않는 것:** Tailwind, Redux, Three.js/WebGL, Notion API, CMS, 별도 백엔드. 추가하려면 승인이 필요하다.
- **언어:** `ko`(기본), `en`, `ja`. 라우트는 `/[locale]`, `/[locale]/projects/[slug]`.
- **테마:** 라이트/다크. `next-themes`가 `data-theme` 속성으로 전환한다. 전환 시 View Transitions로 0.45초 교차한다. 색은 `styles/tokens.css`의 CSS 변수만 쓴다.
- **디자인 토큰:** 포인트 컬러 라이트 `#0071e3`, 다크 `#0a84ff`. 글래스는 `--glass-bg`, `--glass-border`, `--glass-highlight`, `--glass-shadow`, `--glass-blur`를 쓴다. 간격·글자 크기·자간도 `tokens.css` 변수를 쓴다.
- **폰트:** 한국어 Paperlogy(`fonts/`에 직접 호스팅), 일본어 M PLUS 1, 영문 Anybody(`next/font/google`). 라틴 글자는 영문 폰트가, 한글은 한국어 폰트가 맡는다. 폰트를 추가·교체하면 `fonts/README.md`에 출처와 라이선스를 기록한다. 라이선스가 확인되지 않은 폰트는 넣지 않는다.
- **Header:** 왼쪽 `Projects`, 가운데 워드마크 `Heo Jae Won`, 오른쪽 언어(`KO/EN/JP`)·테마 버튼. 스크롤하면 글래스 배경과 하단 진행 바가 나타난다.
- **도메인:** `https://ja2x0n-portfolio.kro.kr` (내도메인.한국 → Vercel). `.vercel.app` 주소는 Vercel 배포 보호로 로그인이 필요하다.
- **폴더:** `app/[locale]/`, `components/`(`Header/`, `Section/`, `sections/`), `content/`, `messages/`, `i18n/`(`routing.ts`, `request.ts`, `navigation.ts`), `styles/`, `fonts/`, `public/`.
- **내부 링크:** 언어를 유지해야 하므로 `next/link` 대신 `@/i18n/navigation`의 `Link`를 쓴다.
- **프로필 사진(확정):** Home에 증명사진을 넣는다. 파일은 `public/images/profile.*`에 두고 `next/image`로 표시한다. 대체 텍스트는 `messages/*.json`에 언어별로 쓴다. 사진 파일은 사용자가 제공한다. 없으면 만들거나 임의 이미지로 대체하지 않는다.
- **콘텐츠 분리:** UI 문구는 `messages/*.json`, 프로젝트·경력·기술 데이터는 `content/*.ts`.
- **명령어:** `npm run dev`, `lint`, `typecheck`, `build`, `format`. 이 목록에 없는 명령은 실행하기 전에 `package.json`에서 확인한다.

## 3. 승인 게이트

AI는 아래 단계에서 **자동으로 다음 단계로 넘어가지 않는다.** 요청 후 명시적 승인을 기다린다.

| 게이트                        | 승인자 |
| ----------------------------- | ------ |
| 구현 결과 컨펌 (**커밋 전**)  | 사용자 |
| 설계·정책 변경                | 사용자 |
| PR **Merge** (§12 Merge 규칙) | 사용자 |
| 배포 설정, 도메인 연결        | 사용자 |

승인이 없으면 다음 작업으로 넘어가지 않는다. "괜찮아 보인다"는 승인이 아니다.

### 반드시 먼저 승인받는 변경

**구조·의존성**

- 라이브러리 추가·제거·대규모 버전 변경
- 폴더 구조 대규모 변경, 대규모 리팩터링
- `next.config.ts`, `proxy.ts`, `tsconfig`, ESLint 설정 변경
- CI/CD, 배포, 도메인, 환경변수 변경

**사용자에게 보이는 계약**

- 라우트(URL) 추가·변경·삭제
- `messages/*.json` 키 삭제·이름 변경
- 지원 언어 추가·제거
- 디자인 토큰의 의미 변경 (색 이름, 라이트/다크 대응 관계)

**설계서에서 "검토 중"으로 남은 결정**

- 포인트 컬러, 폰트 조합, 배경 그래픽 사용 여부
- 임시값을 넣은 경우 코드에 `// TODO(decision):` 표시하고 보고한다.

**콘텐츠 (사실 관계)**

- 프로젝트 기여 범위, AI 활용 범위, 성과 수치, 수상·경력 문구를 새로 쓰거나 바꿀 때

**Git**

- force push, 브랜치·태그 삭제 (Merge 후 작업 브랜치 삭제는 제외)
- Merge — 사용자가 해당 PR의 Merge를 직접 지시한 경우에만 한다 (§12)
- `main` 직접 push (§6의 오타·문구 한 줄 예외는 제외)

승인 요청 형식:

```text
[변경 승인 요청]
변경 대상:
변경 이유:
현재 → 변경 후:
영향받는 화면·라우트·언어:
위험 요소:
대안:
추천:
```

## 4. 콘텐츠 정직성 규칙 (포트폴리오 고유)

이 사이트의 신뢰도는 콘텐츠의 정확성에 달려 있다. 아래는 예외 없이 지킨다.

- 사용자가 직접 제공하지 않은 경력, 수상, 수치, 기술 사용 경험을 만들어 넣지 않는다.
- 팀 결과와 개인 기여 범위를 구분해서 쓴다.
- AI가 작성한 코드를 직접 작성한 것처럼 쓰지 않는다. CapTeam의 후반 구현은 AI 활용 비중이 높았다는 사실을 설계서 기준으로 정확히 쓴다.
- JICHINI의 폴더 구조와 컴포넌트 책임을 성공 사례처럼 포장하지 않는다.
- 성과 수치는 확인 가능한 근거가 있을 때만 쓴다.
- **전화번호는 공개 사이트에 넣지 않는다.** 코드, 번역 파일, 메타데이터, 로그, 문서 어디에도 쓰지 않는다.
- 이메일·SNS 링크는 설계서 `01. 포트폴리오 목표`의 공개 연락 채널만 쓴다.
- 영어·일본어 번역을 만들 때 의미를 부풀리지 않는다. 확신이 없으면 표시하고 사용자에게 확인받는다.
- 이름, 기술명, 브랜드명은 번역하지 않는다.

## 5. 작업 원칙

1. **한 번에 하나:** Issue 1개 = 브랜치 1개 = 기능 1개 = PR 1개. 진행 중인 Issue가 끝나기 전에 다른 기능을 시작하지 않는다.
2. **요청 범위만:** 요청에 없는 리팩터링·정리·기능을 끼워 넣지 않는다.
3. **재사용 우선:** 새 코드를 쓰기 전에 기존 컴포넌트, 토큰, 유틸이 있는지 확인한다.
4. **가장 단순하게:** 네이티브 기능(CSS, HTML)이 되면 JS를 쓰지 않는다. 추상화는 두 번째 사용처가 생길 때 만든다.
5. **확인한 것만 보고:** 실행하지 않은 명령, 확인하지 않은 화면을 "통과"로 쓰지 않는다.
6. **모르면 묻는다:** 추측으로 채우지 않는다.

새 요청이 현재 범위를 벗어나면:

```text
현재 작업 범위를 벗어난 요청입니다.
현재 브랜치에 넣으면 변경 범위와 검토 부담이 커집니다.
별도 Issue로 분리하는 것을 제안합니다.
```

현재 기능의 QA 중 발견한 버그는 같은 브랜치에서 고친다. 무관한 버그, 머지 후 회귀, 범위 밖 개선은 별도 Issue다.

## 6. 브랜치와 커밋

**브랜치**

```
{type}-{이슈번호}-{작업명}
type: feat | fix | refactor | docs | test | chore
작업명: 짧은 영문 소문자, 단어는 하이픈으로 연결
예: feat-3-project-carousel
    fix-5-dark-flash
```

- 브랜치는 `main`에서 분기한다. 이슈 1개당 브랜치 1개다.
- 흐름: `main` ← 작업 브랜치 ← PR. 별도 `dev`/`staging`은 두지 않는다. (Vercel이 PR마다 Preview 배포를 만든다.)
- 시작 시 `git branch -a`로 실제 구조를 확인한다. 다르면 보고한다.

**main 직접 커밋 예외 (Issue·브랜치·PR 없음)**

- 대상: 오타 수정, 문구 한 줄 수정.
- 제외: 로직, 스타일, 라우트, `messages` 키 이름, 의존성, 설정 변경. 이런 변경은 예외가 아니다.
- §4 콘텐츠 정직성 규칙이 걸린 문구(경력, 수상, 수치, 기여 범위, AI 활용 범위)는 한 줄이어도 예외가 아니다. 사용자에게 먼저 확인한다.
- 커밋 메시지는 `docs(scope): ...` 또는 `fix(scope): ...` 형식을 그대로 쓴다.

**커밋 (GONE 규칙 유지)**

```
<type>(<scope>): <한글 설명>
예: feat(carousel): 프로젝트 수동 캐러셀 구현
    fix(theme): 다크모드 첫 렌더 깜빡임 수정
    chore(deps): Prettier 설정 추가
```

- 설명은 한글, 현재형. 작은 단위로 커밋한다. 목적이 다른 변경을 섞지 않는다.
- 커밋 끝에 harness가 지정한 Co-Authored-By 줄을 붙인다.
- 커밋을 분리하기 어려우면 먼저 커밋 계획을 설명한다.

## 7. Issue

**기능 Issue** — 제목, 배경, 목표, 작업 범위, **범위에 포함하지 않는 것**, 영향 화면·라우트, 언어·테마·반응형 영향, 완료 조건(체크리스트), 위험 요소.
**버그 Issue** — 발생 환경(브라우저·뷰포트·언어·테마), 재현 방법, 실제/기대 결과, 원인 추정, 수정 계획, 완료 조건.

- GitHub 조작은 `gh` CLI를 쓴다. (GitHub MCP는 연결이 불안정할 수 있다.)
- 라벨은 기존 라벨을 먼저 확인한다. 기본 분류: `feature` `bug` `docs` `refactor` `test` `chore`, `priority:*`, `needs-discussion`, `blocked`.
- 현재 작업과 무관한 문제를 발견해도 자동으로 Issue를 만들지 않는다. 제안만 한다.

## 8. 작업 흐름

각 단계 끝의 **[STOP]**은 사용자 승인 대기 지점이다.
오타·문구 한 줄 수정은 이 흐름을 따르지 않는다. (§6 예외)

```
1. Issue 생성        사용자가 말한 작업을 먼저 Issue로 만든다 (§7, 계획 포함)
2. 조사             설계서, 관련 코드, Next.js 문서, 기존 컴포넌트·토큰
3. 브랜치 생성       main에서 분기, 이름은 §6 규칙
4. 구현             Issue 범위 안에서 작업한다. 이 단계에서는 커밋하지 않는다
5. 자체 검증         §10 체크리스트 실행 (브라우저 확인 포함)
6. 컨펌 요청         변경 요약 + 검증 결과 + 위험 지점 (§11)
                    [STOP] 사용자 컨펌 전에는 커밋하지 않는다
7. 수정 반영         의견 반영 후 §10 재실행, 다시 컨펌 요청 (반복)
8. 커밋             컨펌 후 목적별로 나눠 커밋한다 (§6)
9. push + PR 생성    §12 형식으로 main 대상 PR을 만든다
                    [STOP] Merge는 사용자 지시가 있을 때만 (§12)
10. Merge           Squash merge → 작업 브랜치 삭제 → main 동기화 → 운영 반영 확인
11. 설계서 반영      Merge된 뒤에만 Notion 설계서·체크리스트 갱신
```

구현 중 Issue의 범위나 계획이 달라지면 §13을 따른다.

사용자가 한 번에 여러 단계를 지시하면(예: "커밋하고 PR 만들고 머지까지") 지시한 단계까지 진행한다. 지시에 없는 단계는 건너뛰지 않고 멈춘다.

작업 시작 보고 형식:

```text
[요청 이해]        한 문장
[기존 코드 확인]   관련 파일과 재사용할 것
[관련 문서]        설계서 페이지, Next.js 문서
[변경 예정 파일]
[검증 계획]        §10 중 어떤 항목을 어떻게
[승인 필요 여부]   §3 해당 항목
```

## 9. 작업 계획 (스펙)

계획은 Issue 본문에 쓴다. 기능이 커서 Issue에 담기 어려울 때만 `docs/`에 Markdown 파일을 만든다.
포함 항목:

- 목적, 범위, 범위 밖
- 화면 동작 (정상 흐름, 예외 흐름)
- 영향받는 라우트, 컴포넌트, `messages` 키, `content` 데이터, 디자인 토큰
- 언어(ko/en/ja)별 문구와 길이 변화 대응
- 라이트/다크 대응
- 반응형 동작 (390 / 412 / 768 / 데스크톱)
- 모션: 어떤 요소가 어떻게 움직이는지, `prefers-reduced-motion`에서의 동작
- 접근성: 키보드 조작, 포커스, 대체 텍스트
- 완료 조건

문장은 구체적으로 쓴다.

- 나쁨: "적절히 처리한다", "필요할 수 있다"
- 좋음: "`prefers-reduced-motion: reduce`이면 슬라이드 이동 대신 opacity 전환만 적용한다."

## 11. 컨펌 요청 (코드 리뷰)

AI는 컨펌을 요청하고 결과를 정리한다. **컨펌 완료 처리는 사용자가 한다.**

요청 시 제공:

- 변경 파일 요약과 이유
- 설계서·계획과 다르게 구현한 부분
- 위험하거나 확신이 낮은 지점
- 확인하지 못한 항목

리뷰에서 볼 것: 계획 범위 이탈, 기존 컨벤션 불일치, 토큰 하드코딩, 번역 누락, 접근성 누락, 모션 감소 미대응, 불필요한 복잡도, 불필요한 클라이언트 컴포넌트(`"use client"`), 번들 크기 증가, 비공개 정보 노출.

발견 사항은 Critical → High → Medium → Low 순으로 정리한다. 각 항목에 문제 요약, 재현 조건, 영향, 파일·위치, 해결안(장단점), 추천안을 쓴다. 문제가 없어도 확인한 범위와 확인하지 못한 부분을 기록한다.

리뷰 결과는 PR 본문에 포함한다. 규모가 크면 `docs/`에 별도 파일로 둔다.

## 12. Pull Request

- push·PR 생성 전 §10 통과, 사용자 컨펌, 커밋 정리를 확인한다.
- 검토가 끝나기 전에 다음 독립 작업을 시작하지 않는다.

**Merge 규칙**

- 사용자가 **그 PR의 Merge를 직접 지시한 경우에만** Merge한다. 이전 PR에서 받은 지시는 다음 PR에 적용하지 않는다.
- 방식은 Squash merge다: `gh pr merge <번호> --squash --delete-branch`
- Merge 후 `main`으로 전환해 `git pull`하고, 연결된 Issue가 닫혔는지 확인한다.
- `main` push는 곧 운영 배포다. Merge 후 운영 도메인에서 변경이 반영됐는지 확인하고 보고한다.
- 본문에 반드시 포함:

```text
## 목적 / 관련 Issue
## 변경 내용
## 변경하지 않은 내용
## 영향 범위 (라우트 / 언어 / 테마 / 반응형)
## 검증 결과 (실행한 명령과 결과, 미실행 항목 명시)
## 코드 리뷰 결과
## 알려진 문제·남은 작업
## 배포 시 주의사항
```

- 본문 끝에 harness가 지정한 PR 서명 줄을 붙인다.
- 생성 후 보고: PR 링크, 관련 Issue, 변경 범위, 검증 결과, 검토가 필요한 내용, Merge 전 확인 사항.

## 13. 설계 변경 처리

구현 중 계획과 달라지는 경우:

| 경우                                                                              | 처리                                                |
| --------------------------------------------------------------------------------- | --------------------------------------------------- |
| 내부 구현만 다름 (변수명, 내부 구조, 알고리즘, 사용자에게 안 보이는 리팩터링)     | 계획 문서를 실제와 맞추고 계속 진행. PR에 명시한다. |
| 라우트, 문구 키, 화면 동작, 모션 방식, 접근성 정책, 토큰 의미, 지원 환경이 달라짐 | **구현을 멈추고** 아래 형식으로 재승인을 받는다.    |

```text
[설계 변경 요청]
기존 설계:
변경하려는 설계:
변경 이유:
영향 (화면 / 언어 / 테마 / 반응형 / 접근성):
대안:
추천:
```

승인 전에는 변경된 정책을 코드에 반영하지 않는다.

## 14. 보안·개인정보

- `.env*`, 토큰, API 키를 커밋하지 않는다. 클라이언트에 노출되는 `NEXT_PUBLIC_*`에 비밀값을 넣지 않는다.
- 로그·문서·PR·커밋 메시지에 개인정보 원문(전화번호 등)을 쓰지 않는다.
- 외부 링크는 `rel="noopener noreferrer"`를 쓴다.
- 서드파티 스크립트(분석, 폰트 CDN 등)를 추가하려면 승인받는다.

## 15. 완료 보고 형식

```text
[작업 완료]
작업 내용:
변경 파일:            경로: 변경 내용
영향 범위:            라우트 / 언어 / 테마 / 반응형 / 변경 없음
검증:                 실행한 명령, 통과 여부, 실패 항목, 미실행 항목
브라우저 확인:         확인한 언어·테마·뷰포트
코드 리뷰:             요청 여부, 결과, 반영 내용
PR:                   링크, Merge 전 남은 작업
설계서 반영:           필요 여부, 상태
남은 문제:             해결하지 못한 것, 별도 Issue가 필요한 것
```

확인하지 않은 항목은 "확인 완료"로 쓰지 않는다.

## 16. 행동 요약

- 코드보다 먼저 읽는다: `AGENTS.md`, 설계서, 기존 코드.
- Next.js 16 문서를 확인하고 기존 지식으로 쓰지 않는다.
- 요청 범위만 바꾼다. 하나의 Issue, 하나의 브랜치, 하나의 PR.
- 사실 관계가 걸린 콘텐츠는 만들지 않는다.
- 브라우저에서 직접 확인하고, 확인한 것만 보고한다.
- 커밋 전에 컨펌을 받는다. Merge는 사용자가 지시한 PR만 한다.
- 모르면 추측하지 않고 묻는다.
